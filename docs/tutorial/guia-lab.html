Quest 3 no 5G do lab → servidor Linux

Guia do dia do teste · servidor 172.30.22.31 (servidorNetuno) · porta UDP 7777
[Quest 3 com o app] --Ethernet--> [Roteador 5G do lab] --5G--> [Rede 5G] --cabo--> [servidorNetuno 172.30.22.31] cliente (APK) servidor dedicado (ConsultorioServer)

1. O que já está pronto

ItemEstado
Servidor Linux em ~/consultorio-build (release servidor-v2)Pronto. Já rodou, escutou em 0.0.0.0:7777 e iniciou como servidor dedicado.
APK instalado no QuestPronto. O log do Quest mostrou Iniciando como CLIENTE conectando em 172.30.22.31:7777.
Porta 7777/udp no firewall do servidorLiberada (ufw allow 7777/udp).
Quest alcançando o servidor pela rede 5GFalta testar. Em casa o Quest estava no Wi-Fi 192.168.1.x, que não alcança o servidor. É o objetivo do dia no lab.

Como funciona: o servidor roda o cenário sem gráficos e é o dono da sala. O Quest abre o app, conecta no IP do servidor e, se falhar, tenta de novo sozinho (a primeira tentativa dura cerca de 1 minuto, depois repete a cada 3 s). Não existe botão nem campo de IP dentro do app: o IP já está dentro do APK.

2. O que levar

  • Quest 3 carregado (com o app Consultorio VR já instalado)
  • Adaptador USB-C → Ethernet (de preferência com entrada de carga) e um cabo de rede
  • Cabo USB-C de dados e o computador com adb, se quiser ver o log do Quest (opcional)
  • Usuário e senha do servidor (admin)

3. Passo a passo no lab

Use o computador do lab, ligado ao cabo da rede DCC. Você vai abrir duas janelas do PowerShell, e cada uma entra no servidor por SSH.

Janela 1 Subir o servidor

ssh admin@172.30.22.31

Antes de subir, veja se ele já está rodando (da última vez ele ficou aberto):

ss -ulpn | grep 7777
  • Aparece uma linha com ConsultorioServ: já está rodando. Para recomeçar limpo, pare e suba de novo: 
    pkill -f ConsultorioServer.x86_64
tmux kill-session -t vr
  • Não aparece nada: siga direto para o próximo bloco.

Suba o servidor dentro do tmux, com o log em arquivo (assim ele não para se você fechar a janela):

tmux new -s vr
cd ~/consultorio-build
./ConsultorioServer.x86_64 -logFile ~/server.log

Esse terminal fica "parado" porque o servidor está rodando. Para sair do tmux sem parar o servidor: aperte Ctrl+B, solte, e aperte D. Para voltar a ele depois: tmux attach -t vr.

Confirme que o servidor subiu (em um terminal livre):

ss -ulpn | grep 7777
grep "SERVIDOR DEDICADO" ~/server.log

Devem aparecer a linha com 0.0.0.0:7777 e a mensagem --- LAN: Iniciando como SERVIDOR DEDICADO na porta 7777 ---.

Janela 2 Ver os pacotes chegando

Abra outro PowerShell no computador do lab:

ssh admin@172.30.22.31
sudo apt install -y tcpdump
sudo tcpdump -ni ens18 udp port 7777

O tcpdump roda dentro do servidor, porque é lá que o tráfego do Quest chega. Deixe essa janela aberta. Para parar, aperte Ctrl+C.

Ligar o Quest na rede 5G

  1. Encaixe o adaptador USB-C → Ethernet no Quest e ligue o cabo de rede no roteador 5G do lab.
  2. No Quest: Configurações → Wi-Fi e desligue o Wi-Fi, para o tráfego ir só pelo cabo.
  3. Abra o app: Biblioteca → Fontes desconhecidas → Consultorio VR.

Como saber que deu certo

OndeO que aparece
Janela 2 (tcpdump)Linhas como IP_DO_QUEST.porta > 172.30.22.31.7777. O IP de origem é o do Quest na rede 5G: anote.
Dentro do QuestVocê entra no consultório e o app deixa de ficar "tentando conectar".
Com 2 ou mais QuestsCada um vê o avatar do outro e ouve a voz dele.
No servidor, o log ~/server.log cresce quando clientes entram (use tail -f ~/server.log para acompanhar). O servidor ainda não escreve uma frase do tipo "cliente conectado", por isso o tcpdump é a prova principal de que o tráfego chega.

4. Se não conectar

O que você vêO que significa e o que fazer
tcpdump não mostra nenhum pacote depois de ~1 min com o app abertoO Quest não alcança o servidor. Confira: (1) o Quest está no cabo e o Wi-Fi está desligado? (2) qual IP o Quest recebeu (veja abaixo)? (3) o roteador 5G tem rota até a rede 172.30.22.0/24? Se não souber, pergunte ao professor em que ponto o servidor está ligado.
tcpdump mostra pacotes, mas o Quest não entra no cenárioOs pacotes chegam e a resposta não volta. No servidor, rode ip route e me mande a linha default via .... A rede do Quest precisa ter rota de volta pelo mesmo roteador.
O app fica "tentando conectar"É a reconexão automática: ela tenta a cada 3 s. Aguarde alguns minutos antes de concluir que falhou.
ss -ulpn | grep 7777 não mostra nadaO servidor não está rodando. Entre com tmux attach -t vr, ou veja o fim do log: tail -n 30 ~/server.log.
Address already in use ao subir o servidorJá existe um servidor rodando. Use pkill -f ConsultorioServer.x86_64 e suba de novo.
Sem vozNo Quest: Configurações → Apps → Consultorio VR → permitir Microfone.
Um avatar parado na origem, sem donoÉ o avatar do próprio servidor, esperado nesta versão (v2). A correção já existe no projeto (commit 90fc111) e entra na versão v3 do servidor.

Como descobrir o IP do Quest no cabo

  • Pelo roteador 5G: a página de administração dele costuma ter a lista de dispositivos conectados (DHCP clients).
  • Pelo adb: com o Quest no USB do computador (sem o adaptador Ethernet), rode 
    adb shell ip -4 -br addr
    Se não tiver o adb no computador do lab, o do Unity fica em C:\Program Files\Unity\Hub\Editor\6000.0.39f1\Editor\Data\PlaybackEngines\AndroidPlayer\SDK\platform-tools\adb.exe.
  • Meta Quest Developer Hub (opcional): não é necessário para o teste. Se preferir uma tela, ele mostra o IP e os logs do Quest em Device Manager, mas exige instalar e entrar com a conta Meta.
  • Em casa o Quest estava em 192.168.1.x (Wi-Fi). No lab o IP deve ser de outra faixa.

Conferir a rota a partir de um PC na rede 5G

tracert 172.30.22.31

Latência abaixo de 1 ms indica rede local (sem o 5G no caminho).
